Five GPOs, each linked on purpose

Open one to see why it sits where it sits, and how I proved it.

Default Domain Policydomain root

Password length 14, history 24, complexity on. Lockout after 5 attempts for 15 minutes. Account policy is only read from the GPO linked at the root. Proof: Get-ADDefaultDomainPasswordPolicy, then a real lockout test on a test user and Unlock-ADAccount.

GPO-Workstation-BaselineDepartments

Firewall on in all profiles with inbound blocked, screen lock at 10 minutes, SMBv1 disabled. One link on the parent OU reaches every child. Proof: gpresult, Get-NetFirewallProfile, EnableSMB1Protocol False.

GPO-Local-AdminsDepartments

SG_IT_Admins added to local Administrators. People go into groups, groups go onto resources, nobody is named directly. Proof: elevation worked for the admin account and failed for a standard IT user.

GPO-Operations-RestrictionsOperations/Users

Control Panel and Settings blocked. User-side settings follow the user object. Proof: blocked for one user, normal for another user in a different OU.

GPO-Security-PSLoggingSecurity/Computers

PowerShell script block logging, event 4104. Computer-side scope follows the computer object. Proof: see the live test below.

      Incident log

      Three real incidents from my lab, each with root cause, fix and verification. Open one.

      Wrong VM renamedSep 24

      Cause: DC01 was renamed to WIN11-01 in the wrong console (computer objects cannot be renamed from ADUC by design). Fix: snapshot first, rename back from the machine, delete the stale DNS record. Verified: RootDSE dnsHostName, the _ldap and _kerberos SRV records and every SPN pointed at DC01 again.

      WAN routing broken after rebootSep 16

      Cause: no default gateway pinned in pfSense, so automatic selection picked the LAN gateway on every reload. Fix: pin WAN_DHCP as default gateway. Verified: gateway status showed WAN as default and internet came back.

      Alert lost in the same outage as the reportSep 27

      Cause: a DNS blip broke the report, and the failure alert hit the same blip. Fix: SMTP retries with a local failure log. Verified: retry logic tested with a mocked client that failed twice, then recovered.

      A deploy robot with minimal rights

      CI/CD from GitHub to my Proxmox node.

      1. A push to GitHub starts the deploy workflow.
      2. The runner joins my private Tailscale network with a tagged OAuth client that can reach one host on one port and nothing else.
      3. It logs in with a restricted SSH key. The lock on the host limits what the key may run.
      4. A watchdog timer checks the result every 60 seconds and keeps a log.
      5. No secrets live in the repo. Keys are GitHub secrets, with a rotation procedure written in the docs.
